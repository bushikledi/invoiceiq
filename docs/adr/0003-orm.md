# 3. Prisma 6 (not 7) as the ORM

**Status:** Accepted · **Date:** 2026-07-26

## Context

We need migrations, type-safe queries, and pgvector. Prisma 7.9 was the current
release when this was written; Prisma 6.19 was the previous major.

## Decision

Pin Prisma to **6.19.2**.

Prisma 7 ships as ES modules only and requires a driver adapter for every
database. Adopting it would mean `"type": "module"` across all three
applications — and NestJS's decorator metadata, `@nestjs/cli` builds, and much
of its ecosystem are still most reliable under CommonJS. That is a large,
cross-cutting risk to absorb for no capability we actually need: the one thing
Prisma cannot do here is pgvector, and Prisma 7 does not fix that either.

## Consequences

**Good.** CommonJS everywhere; no ESM interop debugging. The 6.x line is still
supported.

**Bad.** One major version behind, and `prisma-client-js` is on Prisma's
deprecation path.

**Migration path when it is worth it:** switch the generator to
`prisma-client`, add `@prisma/adapter-pg`, set `"type": "module"` and
`"module": "ESNext"` per app, and expect to fix Nest bootstrap and Vitest
config. Nothing in the application code changes, because every Prisma call site
already lives behind `packages/database`.

## Notes on pgvector

Prisma has no native `vector` type. The embedding column is declared
`Unsupported("vector(384)")`, and reads/writes go through `$queryRaw` inside
`packages/database` — never leaking outward. `CREATE EXTENSION vector` and the
HNSW index live in hand-written migration SQL, because neither the extension
ordering nor the index is expressible in the Prisma schema.

Two operational details worth remembering:

- `prisma migrate dev` is **interactive**. It prompts, and under a non-TTY
  (CI, Docker, a scripted bootstrap) it hangs indefinitely. Automation uses
  `migrate deploy`; `migrate dev` is for authoring migrations by hand.
- `prisma` is a **runtime** dependency, not a dev one, because the deploy runs
  `prisma migrate deploy` as a release command and the CLI has to exist in the
  shipped image.

## Alternatives

- **Drizzle.** Genuinely attractive here: first-class `vector` columns, native
  HNSW index declarations, and a `cosineDistance` helper would remove the raw
  SQL entirely. Rejected only because Prisma's migration tooling is better and
  the raw-SQL surface is small and contained. This remains the fallback if the
  pgvector escape hatch becomes unwieldy.
- **TypeORM / Kysely.** Weaker migration DX and weaker inference respectively.
